## 1. Scope, conventions and notation

### 1.1 Scope

In scope: pairing a phone with a Mac (QR and 6-digit code), the persisted trust relationship ("binding"),
session establishment and authentication, scope enforcement, the fail-closed lease contract, key rotation,
device loss, revocation, downgrade resistance, and the small amount of discovery cryptography (the rotating
DNS-SD token) and side-effect cryptography (the `op_id` payload hash).

Out of scope: the 0.1–0.2 ADB trust path ([architecture §8](../architecture.md#8-security-model), "documented
exception"), the helper ↔ app channel (S12), media framing, file-transfer integrity (BLAKE3, protocol §8),
remote access through a relay (v2), and discovery UX.

### 1.2 Requirements language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**,
**RECOMMENDED**, **NOT RECOMMENDED**, **MAY** and **OPTIONAL** are to be interpreted as described in BCP 14
(RFC 2119, RFC 8174) when, and only when, they appear in all capitals.

### 1.3 Notation

| Notation | Meaning |
|---|---|
| `a ‖ b` | byte-string concatenation |
| `x[i..j]` | bytes `i` (inclusive) to `j` (exclusive) of `x` |
| `u8(v)`, `u32be(v)`, `u64be(v)` | unsigned integer `v` as 1, 4 or 8 bytes, big-endian |
| `i32be(v)` | signed 32-bit integer, two's complement, big-endian |
| `"text"` | the ASCII / UTF-8 bytes of the text, no terminator |
| `H(x)` | SHA-256 |
| `HMAC(k, m)` | HMAC-SHA256 (RFC 2104), full 32-byte output |
| `HKDF-Extract(salt, ikm)`, `HKDF-Expand(prk, info, L)` | HKDF with SHA-256 (RFC 5869). An empty salt means 32 zero bytes (RFC 5869) |
| `HKDF(salt, ikm, info, L)` | `HKDF-Expand(HKDF-Extract(salt, ikm), info, L)` |
| `Sign(K, m)` / `Verify(K, m, σ)` | ECDSA over P-256 with SHA-256 applied to `m` (§5.4) |
| `Exp(label)` | `TLS-Exporter(label, context = empty, length = 32)` on the current connection (RFC 8446 §7.5) |
| `enc(label; f1, …, fn)` | canonical transcript encoding (§5.2) |
| `seq(x1, …, xk)` | canonical list encoding (§5.2) |
| `CT-EQ(a, b)` | constant-time equality of two byte strings |
| `n` | order of the P-256 group, `FFFFFFFF00000000FFFFFFFFFFFFFFFFBCE6FAADA7179E84F3B9CAC2FC632551` |
| `OS2IP(x)` | `x` read as a big-endian unsigned integer |
| `b64u(x)` | base64url without padding (RFC 4648 §5) |

**Device roles** are fixed: **PHONE** (the Android device, media sender and capability provider) and **MAC**
(the controller). **Connection roles** are per connection: the **dialer** (QUIC/TLS client) and the
**listener** (QUIC/TLS server). Either device may be either connection role (§6).

## 2. Actors and trust assumptions

| Actor | Description | Trusted for |
|---|---|---|
| Phone owner | Person holding the unlocked phone | Granting and revoking scopes; approving pairing on the phone |
| Mac user | Person at the Mac | Starting pairing; confirming pairing and control (Touch ID / password) |
| Phone app | Tombolo for Android with `tombolo-core` | Enforcing scopes and the lease; owning the phone's keys |
| Mac app | Tombolo for Mac with `tombolo-core` | Owning the Mac's keys and pairing tickets |
| Hardware key stores | Mac Secure Enclave; Android StrongBox / TEE (KeyMint) | Non-exportability of identity keys; the Mac's user-presence check |
| Helper | Optional shell-uid `tombolo-helper` (Enhanced mode) | Nothing beyond what S12 establishes; it obeys the lease |
| Network, USB/adb tunnel, DNS-SD | Everything between the two apps | **Nothing.** All of it is attacker-controlled in this model |

Assumptions: both apps and their OS are not compromised (a rooted phone and same-user Mac malware with TCC
grants are out of scope, as in [threat model](../research/04-transport-and-security.md#54-threat-model) T5/T8);
each platform provides a cryptographically secure RNG; hardware key stores behave as documented.

## 3. Transport assumptions

This design relies on the following properties of the transport. **A2, A3 and A5 are being verified for
iroh/noq by spike S5 (P0-14); this specification cannot be final until S5 reports.** If S5 finds a gap, the
fallback is the one recorded in [research P2](../research/04-transport-and-security.md#10-open-questions--needs-prototyping)
(patch, or our own UniFFI crate over quinn/rustls); the security design does not change.

| # | Assumption |
|---|---|
| A1 | Every connection is QUIC v1 (RFC 9000) secured by TLS 1.3 (RFC 8446, RFC 9001) via **rustls**, or — on paths where S4 rejects QUIC — TLS 1.3 over TCP via rustls inside `tombolo-core` ([ADR-0003](../decisions/0003-transport.md)). No other TLS version and no plaintext mode exist. |
| A2 | The TLS **exporter** (RFC 8446 §7.5) is available to `tombolo-core` on every established connection, with an arbitrary label and length 32. *(S5)* |
| A3 | Authentication is **mutual**, using each device's Ed25519 **transport key** as a raw public key (RFC 7250). The application learns the peer's authenticated transport public key before it processes any application data, and can reject the connection at that point. *(S5)* |
| A4 | ALPN (RFC 7301) is negotiated; the selected protocol is exposed to the application and is covered by the TLS handshake transcript. |
| A5 | The listener can apply a different peer-key policy per ALPN: accept an unknown client key only for `tombolo-pair/1` while a pairing context is open (§7.1), and only known keys for `tombolo/1`. *(S5)* |
| A6 | TLS 1.3 early data (0-RTT) can be disabled in both directions, and session resumption can be disabled. |
| A7 | QUIC datagrams (RFC 9221) are available on QUIC paths; they are protected by the same keys as streams. |
| A8 | On USB the same QUIC/TLS connection runs through the adb-forwarded socket. The tunnel provides **no** authentication or confidentiality; other processes on the phone can reach it ([threat T5](../research/04-transport-and-security.md#54-threat-model)). |

Because the exporter is derived from the TLS 1.3 exporter master secret, which depends on the whole handshake
transcript (both randoms, the key exchange, both raw public keys, ALPN), an exporter value is unique per
connection with overwhelming probability and differs on the two halves of any man-in-the-middle.

## 4. Keys and persisted state

### 4.1 Key inventory

| Key | Algorithm | Scope | Where the private key lives | Purpose |
|---|---|---|---|---|
| **Transport key** `T_X` | Ed25519 | one per device | Software. Encrypted at rest under a hardware-backed wrapping key: Android Keystore AES-256-GCM key; macOS data-protection Keychain item, `…ThisDeviceOnly` | QUIC/TLS raw public key; its public key is the **endpoint ID** (32 bytes) |
| **Identity key** `I_X` | ECDSA P-256 | **one per binding** (generated fresh for every pairing) | Hardware, non-exportable: Mac Secure Enclave; Android StrongBox if available, else TEE | Proves, at pairing and at every session, that the hardware-held key for *this* pairing is at the other end of *this* TLS connection |
| **Presence key** `P_M` (Mac only) | ECDSA P-256 | one per binding | Secure Enclave with access control `.privateKeyUsage` + `.userPresence` | Every use requires Touch ID or the Mac password; proves Mac-user confirmation at pairing and for **elevation** (§9.3) |
| **Pairing secret** `s` (QR) | 256 random bits | one per QR ticket | Mac memory only; phone memory only (from the QR) | One-time proof that the phone saw the QR |
| **Pairing code** (code path) | 6 decimal digits | one per code ticket | Mac memory; typed into the phone | SPAKE2 password (with the exporter) |
| **Discovery key** `DK` | 32 bytes | one per binding | Both bindings, encrypted at rest | Rotating DNS-SD token (§12) |
| **Filler key** `FK` (phone only) | 32 bytes | one per phone | Phone app storage | Indistinguishable padding tokens (§12) |

Rules:

- Identity and presence keys MUST be generated inside the hardware key store and MUST be non-exportable.
  Implementations MUST NOT fall back to software identity keys silently; if the phone has no hardware-backed
  Keystore, pairing MUST warn the owner and record `hw_level = SOFTWARE` in the binding.
- Identity keys are **per binding**, not per device. Deleting a binding therefore deletes the only key that
  can authenticate that pairing (§15), and two Macs cannot link a phone by its identity key. Transport keys are
  per device because the transport endpoint is per device.
- The phone's identity key MUST be usable while the phone is locked (sessions carry notifications while
  locked) and therefore MUST NOT be bound to user authentication. The Mac's identity key SHOULD be usable while
  the Mac's screen is locked but the user is logged in. The presence key MUST require user presence for every
  signature: implementations MUST NOT reuse an `LAContext` authentication (`touchIDAuthenticationAllowableReuseDuration`
  MUST be 0). Exact access-control flags are confirmed by S10.
- Every key used by Tombolo MUST be used only for the purposes in this table. In particular identity and
  presence keys sign only `enc()` transcripts with labels from §5.3.

### 4.2 The binding record

A **binding** is the persisted trust relationship between one phone and one Mac. It ties together the peer's
transport key, the peer's identity key(s) and — on the phone — the scopes.

**Phone-side binding** (authoritative for access):

| Field | Type | Notes |
|---|---|---|
| `pair_id` | 16 bytes | `H(T_cmp)[0..16]` (§7.7); identical on both sides |
| `status` | `UNCONFIRMED` / `ACTIVE` / `REVOKED` | `UNCONFIRMED` until `PairDone` or the first successful session; behaves exactly like `ACTIVE` for security purposes, it only drives UI |
| `peer_endpoint_id` | 32 bytes | Mac transport public key, taken from TLS at pairing |
| `peer_pending_endpoint_id` | 32 bytes or null | During transport-key rotation (§13.1) |
| `peer_identity_pub` | 65 bytes | Mac identity key (SEC1 uncompressed) |
| `peer_previous_identity_pub` | 65 bytes or null | During identity rotation (§13.2) |
| `peer_presence_pub` | 65 bytes | Mac presence key |
| `own_identity_key_alias` | string | Keystore alias of this binding's phone identity key |
| `own_identity_hw` | `STRONGBOX` / `TEE` / `SOFTWARE` | Shown in the UI |
| `scopes` | set of scope names | Granted by the phone owner (§9) |
| `elevation_required` | bool | Default `true` |
| `elevation_scopes` | set of scope names | Default `{screen.control, screen.view}` |
| `screen_paused` | bool | Set by **Stop**; cleared only by the phone owner (§10 rule 4) |
| `discovery_key` | 32 bytes, secret | Encrypted at rest |
| `peer_name` | UTF-8, ≤ 64 bytes | From `PairAccept`; the owner may rename it locally |
| `generation` | u32 | Incremented on every key change |
| `pending_rotation` | `{rotation_id, kind, old alias, new alias}` or null | Initiator side of a key rotation (§13.2) |
| `last_rotation_id` | 16 bytes or null | Receiver side of the last committed rotation (§13.2) |
| `created_at`, `last_session_at`, `revoked_at` | timestamps | Session log and UI |

**Mac-side binding**: `pair_id`, `status`, `peer_endpoint_id` (+ pending), `peer_identity_pub` (+ previous),
`own_identity_key_tag` and `own_presence_key_tag` (Secure Enclave key references), `scopes_hint`,
`elevation_hint`, `discovery_key`, `peer_name`/`model`/`os`, `generation`, `pending_rotation`, `last_rotation_id`,
cached addresses, timestamps. **`scopes_hint` is a UI hint only and MUST NOT be used for any access decision.**

### 4.3 Binding invariants and atomic updates

1. Among bindings with status `UNCONFIRMED` or `ACTIVE`, `pair_id`, `peer_endpoint_id` (current or pending)
   and `peer_identity_pub` (current or previous) are each **unique**. A store that would violate this MUST
   refuse the write.
2. **One record, one lookup.** On a `tombolo/1` connection the binding is found **only** by the
   TLS-authenticated peer endpoint ID. `SessionAuth` is then verified with the identity key **from that same
   record**, and every later decision in that session (scopes, elevation key, lease, journal) uses that record.
   Bindings MUST NOT be looked up by name, discovery token, address or any field carried in a message. (This
   is the lesson of KDE Connect's CVE-2025-66270: identity was checked against one value and trusted for another.)
3. Every change to a binding is a **single atomic transaction** of the binding store (e.g. SQLite in WAL mode
   with `synchronous=FULL`, or write-new-file + `fsync` + atomic rename). A reader sees the record either
   entirely before or entirely after a change. A device MUST commit (durably) **before** it sends the message
   that tells the peer the change happened (`PairComplete`, `PairDone`, `RotateIdentityDone`,
   `RotateTransportDone`).
4. Hardware keys are created **before** the transaction that references them, under a fresh random alias.
   Keys are deleted **after** the transaction that stops referencing them. At start-up each app MUST delete
   every Tombolo hardware key that is referenced neither by a binding nor by a live ticket (orphans from a
   crash). A crash at any point therefore leaves either the old or the new binding, plus at most some orphan
   keys that are garbage-collected.
5. Sessions hold a reference to their binding, not a copy. Each scope check re-reads the current record (or a
   copy-on-write snapshot replaced atomically on every change), so a revocation or scope change applies to the
   next command.
6. The binding store and the transport key MUST be excluded from cloud backup and device-to-device transfer
   (Android: `allowBackup="false"` and data-extraction rules that exclude them; macOS: `ThisDeviceOnly`
   Keychain items, and the store marked excluded from backup). Hardware keys never leave the device, so a
   restored binding would be useless; excluding it avoids confusing half-states.

### 4.4 Ephemeral state

Pairing tickets (§7.2), PAKE scalars, the QR secret, session nonces and session keys exist **in memory only**
and are never written to disk, logs or crash reports.

## 5. Encodings and primitives

### 5.1 Primitive encodings

| Item | Encoding |
|---|---|
| Endpoint ID | 32-byte Ed25519 public key, as used by TLS |
| P-256 public key | SEC1 **uncompressed**, 65 bytes (`0x04 ‖ X ‖ Y`). Receivers MUST reject any other length or prefix, points not on the curve, and the identity element |
| `SPKI(Q)` | DER SubjectPublicKeyInfo for P-256 (RFC 5480): the fixed 26-byte prefix `3059301306072a8648ce3d020106082a8648ce3d030107034200` followed by the 65-byte point (91 bytes total) |
| ECDSA signature | 64 bytes `r ‖ s`, each 32-byte big-endian. Signers convert from the platform's X9.62 DER output. Verifiers MUST reject `r` or `s` outside `[1, n−1]`. Low-S normalisation is **not** required; signatures are never used as identifiers |
| Nonce | 32 bytes from the platform CSPRNG |
| Scope / ALPN names | ASCII |
| Display strings (`name`, `model`, `os`) | UTF-8 exactly as sent; receivers verify transcripts over the received bytes and MUST NOT normalise before verifying. Receivers MUST reject invalid UTF-8, C0/C1 control characters, and strings longer than 64 bytes (`os`: 32), and SHOULD render them with bidi isolation |
| UUID (`op_id`, `transfer_id`) | its 16 octets in RFC 9562 network byte order; `op_id` is a UUIDv7 (§11) |

### 5.2 Canonical transcript encoding

Every MAC and signature in this protocol is computed over a **transcript** built from field values, never over
serialized Protobuf (which is not canonical). The receiver rebuilds the transcript from the values it received
**plus values it knows itself** (its exporter, the TLS-authenticated endpoint IDs, its own nonce).

```
LP(x)                    = u32be(len(x)) ‖ x
enc(label; f1, …, fn)    = LP(label) ‖ u32be(n) ‖ LP(f1) ‖ … ‖ LP(fn)
seq(x1, …, xk)           = u32be(k) ‖ LP(x1) ‖ … ‖ LP(xk)          -- used as a single field value
```

- `label` is an ASCII string from §5.3; it **domain-separates** every use. Each label has exactly one field
  list (fixed count, fixed order, fixed types). There are no optional fields: an absent value is a zero-length
  field, and an optional value that must be distinguishable from "empty" is encoded as `seq()` with zero or one
  element.
- The encoding is injective: the label, the field count and every field are length-prefixed, so two different
  (label, field list) inputs never produce the same bytes.
- Integers inside fields use the fixed-width encodings of §1.3. Booleans are `u8(0)` / `u8(1)`.
- Sets (scopes) are encoded as `seq()` of their elements **sorted by byte-wise ascending order, without
  duplicates**. A receiver that is handed an unsorted or duplicated list in a message MUST reject the message
  (it MUST NOT silently sort it and continue).
- A transcript MUST NOT exceed 64 KiB.
- Role bytes: `ROLE_PHONE = 0x01`, `ROLE_MAC = 0x02`. Method bytes: `METHOD_QR = 0x01`, `METHOD_CODE = 0x02`.

HKDF `info` strings are the plain ASCII labels of §5.3 (no `enc()` wrapper); they are distinct fixed strings.

### 5.4 Primitives

- **Signatures:** ECDSA P-256 with SHA-256 over the transcript bytes (Secure Enclave:
  `ecdsaSignatureMessageX962SHA256`; Android: `SHA256withECDSA`). Hardware signers use random nonces; the test
  vectors use deterministic RFC 6979 nonces so that they are reproducible — verifiers MUST accept any valid
  signature.
- **MACs:** HMAC-SHA256, compared with `CT-EQ`.
- **KDF:** HKDF-SHA256.
- **Exporter:** `Exp(label) = TLS-Exporter(label, "", 32)`. In TLS 1.3 an empty context and no context give
  the same value (RFC 8446 §7.5).
- **Randomness:** every nonce, secret, code and scalar MUST come from the platform CSPRNG. The 6-digit code
  MUST be uniform over `000000`–`999999` (rejection sampling, not `random % 10^6` on a non-multiple range).

## 6. Roles and nonce ownership

- **Device roles are fixed** (PHONE, MAC) and appear in every transcript where a signer could otherwise be
  confused with its peer (`signer_role` fields, distinct labels for request/accept, SPAKE2 roles).
- **Connection roles are free.** In pairing, either device may dial: normally the phone dials the address in
  the QR or the Mac it selected for code entry; over USB the Mac dials the phone through `adb forward`. In
  sessions, either device may dial (protocol §1). Transcripts name the dialer and listener endpoint IDs
  explicitly, so the connection direction is authenticated too.
- **SPAKE2 roles:** A = PHONE, B = MAC, always, independent of the connection role (§7.6).
- **Each side owns exactly the nonces it generates.** A device generates a fresh 32-byte nonce for every
  `PairHello` (`n_P` / `n_M`), every `Hello` (`n_dialer` / `n_listener`) and every elevation challenge (`n_E`,
  phone-owned). Every MAC and signature covers **both** sides' nonces of that connection, so each side gets
  freshness from its own nonce without trusting the peer's RNG.
- A receiver MUST reject a peer nonce equal to its own (reflection). Nonces MUST NOT be reused across
  connections. The nonces are defence in depth: the exporter already differs per connection (§3).
- **Values in transcripts come from the layer that authenticates them.** Endpoint IDs are taken from the TLS
  layer, exporters are computed locally, and own nonces are the locally generated ones. A message field that
  claims an endpoint ID MUST NOT be used.

## 7. Pairing

### 7.1 Common rules

- Pairing runs only on connections whose negotiated ALPN is **`tombolo-pair/1`**. The dialer MUST offer exactly
  one ALPN. A listener MUST NOT negotiate `tombolo-pair/1` unless it has an open **pairing context**: on the Mac a
  live ticket (§7.2); on the phone an open pairing screen (scanned QR waiting for an inbound USB connection, or a
  typed code). Otherwise the handshake fails with `no_application_protocol`.
- On `tombolo-pair/1` an endpoint MAY accept an unknown peer transport key. In the **QR flow the phone MUST
  require the Mac's transport key to equal `id` from the QR**, whichever side dialed.
- The dialer opens the first bidirectional stream (the **pairing stream**). Messages are length-delimited
  Protobuf messages on that stream; any other stream, datagram or message type is a protocol error.
- **Pre-authentication budget** (protocol §8): until the peer has proved the method secret (a valid
  `PairRequest` proof in the QR flow, a valid `cA`/`cB` in the code flow) a connection may buffer at most 16 KiB,
  MUST finish the QUIC handshake and `PairHello` exchange within 5 s, and counts toward the limit of 4
  concurrent unauthenticated connections per device. After that, the human-step timeouts of §7.9 apply.
- `PairError` messages received before the peer has proved the method secret are unauthenticated hints: they
  MUST NOT cause any state change other than ending the local attempt.
- The same flows run unchanged over USB; the adb tunnel is never treated as authenticated (A8).
- In v1, pairing MUST NOT run through a relay.

### 7.2 Pairing tickets (Mac): one-time consumption and attempt limits across connections

A **ticket** is the Mac's record of one open pairing offer. It is the only place where one-time use and attempt
limits are enforced, so they hold **across connections**: a new connection never gets a fresh counter.

**Stored (memory only, in the single process that owns the pairing listener):** `method` (QR / CODE), the
secret (`s`, or the code), the aliases of the freshly generated `I_M` and `P_M`, `created`/`expires` (monotonic
clock), `attempts_left` (3), `state`, `holder` (connection ID), and for QR the phone identity key that consumed it.

**Rules:**

1. At most **one** ticket exists per Mac. Creating a ticket (the user opens "Pair a phone", or switches between QR
   and code) kills the previous one.
2. All ticket transitions happen under one lock as compare-and-set operations. In particular **reserve-then-verify**:
   for the code flow, `attempts_left` is decremented *before* any PAKE computation for that attempt.
3. **Crash safety:** tickets are never persisted. A crash or restart destroys every ticket (and its QR/code
   disappears from the screen with the app), so a crash can never roll a counter back or resurrect a consumed
   secret; it can only end pairing (fail closed). Orphaned keys are collected at start-up (§4.3 rule 4). Exactly
   one process per Mac owns tickets and the `tombolo-pair/1` listener; other processes MUST NOT accept pairing.
4. Expiry is checked at every transition out of `ACTIVE`. A run that started before expiry may finish within its
   step timeouts.
5. When a ticket dies, its secret is wiped and its unused hardware keys are deleted.

| State | Event | Guard / action | Next |
|---|---|---|---|
| — | user opens pairing | generate `I_M`, `P_M`; `s` (32 random bytes) or a uniform 6-digit code; `expires = now + TTL` | `ACTIVE` |
| `ACTIVE` | QR: `PairRequest` with **valid** proof (§7.5) | holder := this connection | `CONSUMED` |
| `ACTIVE` | QR: `PairRequest` with invalid proof | `attempts_left -= 1`; reply `BAD_PROOF`, close | `ACTIVE`, or `DEAD(LIMIT)` at 0 |
| `ACTIVE` | CODE: `PakeA` received | `attempts_left -= 1` **first**; holder := this connection | `IN_USE` |
| `ACTIVE`, `IN_USE`, `CONSUMED` | another connection wants the ticket | CODE: reply `BUSY` before reading `PakeA` (no attempt is charged). QR: see `CONSUMED` row below | unchanged |
| `IN_USE` | valid `cA` | — | `CONSUMED` |
| `IN_USE` | invalid `cA`, step timeout, or disconnect before a valid `cA` | reply `BAD_CONFIRMATION` if possible, close | `ACTIVE` if `attempts_left > 0` and not expired, else `DEAD(LIMIT)` |
| `CONSUMED` | binding committed after a valid `PairComplete` | send `PairDone` | ticket deleted (`DONE`) |
| `CONSUMED` | any failure, timeout, user decline, disconnect | — | `DEAD(FAILED)` |
| `CONSUMED` (QR) | **another** connection presents a **valid** `PairRequest` proof | the QR secret is known to two parties: abort both connections, warn the Mac user ("this code was used by more than one device") | `DEAD(COMPROMISED)` |
| `CONSUMED` (QR) | another connection presents an invalid proof | reply `BAD_PROOF`, close (no state change) | `CONSUMED` |
| `ACTIVE` | `now ≥ expires` | — | `DEAD(EXPIRED)` |
| any live state | user cancels, or a new ticket is created | close the holder connection | `DEAD(CANCELLED)` |
| `DEAD(*)` | — | wipe secret, delete unused keys, update UI | deleted |

**Global back-off:** after 3 tickets have died with `LIMIT` or `COMPROMISED` within 10 minutes, the Mac refuses to
create a ticket for 60 s, doubling on each repetition up to 15 minutes, and tells the user why.

**Phone side:** the phone keeps the scanned QR or typed code in memory only. It runs at most one pairing
attempt at a time, and allows at most 3 failed code confirmations per pairing screen before asking for a new code.
A QR is used for a single connection attempt; if that attempt fails after the phone sent a valid proof, the
ticket is gone and the user needs a new QR.

### 7.3 `PairHello`

Immediately after the handshake, the dialer sends `PairHello`; the listener replies with its own. Then the
method messages start, **always with the phone**.

```
PairHello { version: u32 = 1, role: PHONE|MAC, method: QR|CODE, nonce: bytes[32],
            session_alpns: [string] /* sorted; v1 = ["tombolo/1"] */ }
```

Checks (both sides): `version == 1` else `UNSUPPORTED_VERSION`; roles are one PHONE and one MAC else
`ROLE_CONFLICT`; `method` equals the local pairing context's method else `METHOD_MISMATCH`; peer nonce ≠ own
nonce; `session_alpns` sorted, non-empty and containing a version the receiver supports.

### 7.4 Pairing key schedule

```
exporter_pair  = Exp("tombolo/pair/v1")
method_secret  = s                       (QR:   32 bytes from the QR)
               | Ke                      (CODE: 16 bytes from SPAKE2, §7.6)
ikm_pair       = enc("tombolo/pair/v1/ikm"; u8(method), method_secret)
PRK_pair       = HKDF-Extract(salt = exporter_pair, ikm = ikm_pair)
K_proof_phone  = HKDF-Expand(PRK_pair, "tombolo/pair/v1/key/proof-phone", 32)
K_proof_mac    = HKDF-Expand(PRK_pair, "tombolo/pair/v1/key/proof-mac",   32)
discovery_key  = HKDF-Expand(PRK_pair, "tombolo/pair/v1/key/discovery",   32)
```

`PRK_pair` depends on both the method secret and this connection's exporter, so it is unknown to anyone who
merely saw the QR (they lack the exporter) and differs between the two halves of a man-in-the-middle.

### 7.5 QR flow

**QR payload** (a URI; parameters in this order; binary values `b64u`):

```
tombolo://pair?v=1&id=<b64u(mac endpoint ID)>&a=<addr>,<addr>…&k=<b64u(H(SPKI(I_M.pub)))>&s=<b64u(s)>&exp=<unix seconds>
```

- `a`: up to 8 addresses, `ip:port`; IPv6 as `[addr]:port` with `[`/`]` percent-encoded (`%5B`, `%5D`), no zone ID.
- The phone MUST reject the QR if `v`, `id`, `k`, `s` or `exp` is missing or duplicated, or if `id`, `k`, `s` do
  not decode to exactly 32 bytes. Unknown parameters are ignored. The phone SHOULD warn (not refuse) if `exp`
  is in the past by its own clock; the Mac's monotonic expiry is authoritative.
- `k` commits to the **fresh, per-binding** Mac identity key created with the ticket.
- TTL: default 120 s, configurable 60–300 s.

**Message sequence** (shown with the phone dialing; over USB the Mac dials and the phone listens — the messages
are the same):

```
Phone                                                         Mac (ticket ACTIVE, shows QR)
  scan QR; dial `a`, pin server key == id   ── QUIC/TLS 1.3, ALPN tombolo-pair/1 ──▶
  PairHello{PHONE, QR, n_P}                 ───────────────────────────────────────▶
                                            ◀─────────────────────────────────────── PairHello{MAC, QR, n_M}
  derive PRK_pair from (exporter_pair, s); generate I_P (hardware)
  PairRequest{I_P.pub, name, model, os,
              proof_P, sig_P}               ───────────────────────────────────────▶ verify proof_P (ticket → CONSUMED),
                                                                                     verify sig_P; Touch ID sheet
                                                                                     "Pair with <name> (<model>)?"
                                            ◀─────────────────────────────────────── PairAccept{I_M.pub, P_M.pub, mac_name,
                                                                                       scopes_hint, proof_M, sig_M, sig_PM}
  check H(SPKI(I_M.pub)) == k; verify proof_M, sig_M, sig_PM
  owner chooses scopes and elevation policy; commit binding
  PairComplete{scopes, elevation, sig_C}    ───────────────────────────────────────▶ verify sig_C; commit binding
                                            ◀─────────────────────────────────────── PairDone{}
```

The identity-exchange messages and their transcripts are defined in §7.7 (identical for both flows; in the QR
flow `qr_k = k`).

**Mac connection states (QR):**

| State | Event | Checks | Action | Next |
|---|---|---|---|---|
| `HANDSHAKE` | TLS done, ALPN `tombolo-pair/1` | live QR ticket exists | — | `AWAIT_HELLO` |
| `AWAIT_HELLO` | `PairHello` | §7.3 | send `PairHello`; derive keys | `AWAIT_REQUEST` |
| `AWAIT_REQUEST` | `PairRequest` | proof (`CT-EQ`), then ticket CAS `ACTIVE → CONSUMED` (§7.2), then `sig_P`, key and string validity | show confirmation | `CONFIRM` |
| `CONFIRM` | user approves with Touch ID | `P_M` signs `T_acc` (this signature *is* the confirmation) | `I_M` signs; send `PairAccept` | `AWAIT_COMPLETE` |
| `CONFIRM` | user declines / 60 s | — | `PairError{DECLINED|TIMEOUT}`; ticket `DEAD` | `CLOSED` |
| `AWAIT_COMPLETE` | `PairComplete` | `sig_C`; scope lists canonical | commit Mac binding (atomic, §4.3); send `PairDone` | `DONE` |
| any | error, timeout (§7.9), disconnect, malformed | — | `PairError` if possible; ticket `DEAD` if it was `CONSUMED` by this connection | `CLOSED` |

**Phone states (QR):**

| State | Event | Checks | Action | Next |
|---|---|---|---|---|
| `SCANNED` | QR parsed | §7.5 payload rules | dial addresses in parallel (or accept the Mac's USB dial) | `HANDSHAKE` |
| `HANDSHAKE` | TLS done | Mac transport key `== id`; ALPN | send `PairHello` | `AWAIT_HELLO` |
| `AWAIT_HELLO` | `PairHello` | §7.3 | derive keys; generate `I_P`; send `PairRequest` | `AWAIT_ACCEPT` |
| `AWAIT_ACCEPT` | `PairAccept` | `H(SPKI(I_M.pub)) == k`; `proof_M`; `sig_M`; `sig_PM`; key/string validity | show scope chooser (phone must be unlocked) | `SCOPES` |
| `SCOPES` | owner confirms | at least one scope chosen | commit phone binding as `UNCONFIRMED`; sign; send `PairComplete` | `AWAIT_DONE` |
| `SCOPES` | owner cancels / 120 s | — | `PairError{DECLINED|TIMEOUT}`; delete `I_P` | `CLOSED` |
| `AWAIT_DONE` | `PairDone` | — | binding → `ACTIVE`; show success | `DONE` |
| `AWAIT_DONE` | 10 s or disconnect | — | keep the binding `UNCONFIRMED`; tell the owner pairing may not have finished; the first successful session (§8) promotes it, a rejected one offers removal | `DONE` |
| any earlier state | error / timeout / disconnect | — | wipe `s`; delete `I_P` if no binding was committed | `CLOSED` |

### 7.6 Code flow (SPAKE2, RFC 9382, P-256)

**Ciphersuite:** SPAKE2-P256-SHA256-HKDF-HMAC from RFC 9382 §6, with the RFC's `M` and `N` for P-256 and SEC1
uncompressed point encoding. Cofactor `h = 1`.

**Code:** 6 uniform decimal digits generated by the Mac and **shown on the Mac**; the phone owner types them into
the phone. The phone SHOULD use an in-app digit pad rather than the system keyboard. TTL: default 120 s,
configurable 60–300 s. The Mac MAY advertise a pairing-mode DNS-SD record while the code is shown; discovery is
unauthenticated and never affects trust.

**Inputs** (both sides, after `PairHello`):

```
exporter_pair = Exp("tombolo/pair/v1")
pw  = enc("tombolo/pair/v1/pake/password"; code /* 6 ASCII digits */, exporter_pair)
w   = OS2IP(HKDF(salt = empty, ikm = pw, info = "tombolo/pair/v1/pake/w", L = 40)) mod n
      -- 40 bytes = 64 bits more than n, as RFC 9382 §3.2 suggests; abort if w == 0
A   = phone endpoint ID (32 bytes, from TLS)        -- SPAKE2 identity of A (= PHONE)
B   = Mac endpoint ID   (32 bytes, from TLS)        -- SPAKE2 identity of B (= MAC)
AAD = enc("tombolo/pair/v1/pake/aad"; n_P, n_M, seq(phone session ALPNs), seq(mac session ALPNs))
      -- n_P / the phone's list from the phone's PairHello, n_M / the Mac's list from the Mac's PairHello
```

In `TT` below, `w` is encoded as a **32-byte** big-endian integer, left-padded with zero bytes (RFC 9382 §3.3: "padded
to the length of p"), so `len(w)` is always 32 even when the top byte of `w` is zero; points are 65-byte SEC1
uncompressed, so `len(pA) = len(pB) = len(K) = 65`.

This is the "`password = code ‖ exporter`" design of protocol §6 and of Android Wireless debugging, made
byte-exact. RFC 9382 says `w` SHOULD be derived with a memory-hard function; this design uses HKDF instead
because the password is single-use, never stored, and bound to one TLS connection, so the only attack is online
guessing, which an MHF does not slow down meaningfully (see §20, Q3).

**Protocol** (RFC 9382 §3.3–§4, unchanged): the phone (A) picks `x` uniformly in `[0, n)` and sends
`pA = w·M + x·P`; the Mac (B) picks `y` and sends `pB = w·N + y·P`. Both compute `K` (A: `x·(pB − w·N)`,
B: `y·(pA − w·M)`), then

```
TT        = len(A)‖A ‖ len(B)‖B ‖ len(pA)‖pA ‖ len(pB)‖pB ‖ len(K)‖K ‖ len(w)‖w     (len = 8-byte little-endian, RFC 9382)
Ke ‖ Ka   = H(TT)                                                                   (16 + 16 bytes)
KcA ‖ KcB = HKDF(salt = empty, ikm = Ka, info = "ConfirmationKeys" ‖ AAD, L = 32)
cA = HMAC(KcA, TT)        cB = HMAC(KcB, TT)
```

Every received point MUST be validated (exact 65-byte uncompressed encoding, on the curve, not the identity) and
the protocol MUST abort if `K` is the identity. `x` and `y` MUST be fresh for every run and wiped afterwards.

**Message sequence** (after `PairHello{…, CODE, …}`):

```
Phone (A)                                                    Mac (B, ticket ACTIVE, shows code)
  PakeA{pA}            ────────────────────────────────────▶ ticket: attempts_left -= 1, ACTIVE → IN_USE
                       ◀──────────────────────────────────── PakeB{pB}
  PakeConfirmA{cA}     ────────────────────────────────────▶ verify cA:
                                                               bad → PairError{BAD_CONFIRMATION}; ticket → ACTIVE or DEAD(LIMIT)
                                                               good → ticket → CONSUMED
                       ◀──────────────────────────────────── PakeConfirmB{cB}
  verify cB (bad → abort, count a phone-side failure)
  method_secret = Ke → §7.4 → identity exchange §7.7 with qr_k = empty
```

Neither side considers the PAKE complete before verifying the peer's confirmation (RFC 9382 §3.1). After the
PAKE, the identity exchange is the same as in the QR flow, except that the phone has no `k` to check: the Mac's
identity key is authenticated by `proof_M` (keyed from `Ke`) and by `sig_M` over the exporter-bound transcript.
"Inside the PAKE-derived channel" in protocol §6 is realised this way — the TLS channel already gives
confidentiality, and every identity value is MACed with PAKE-derived keys — rather than with an extra AEAD layer.

**Mac connection states (code):** as the QR table, with `AWAIT_REQUEST` preceded by:

| State | Event | Checks | Action | Next |
|---|---|---|---|---|
| `AWAIT_PAKE_A` | `PakeA` | ticket CAS `ACTIVE → IN_USE` with `attempts_left -= 1` (else `BUSY`/`LIMIT_REACHED`/`TICKET_EXPIRED`); point validity | compute `pB`, `K`, keys; send `PakeB` | `AWAIT_CONFIRM_A` |
| `AWAIT_CONFIRM_A` | `PakeConfirmA` | `CT-EQ(cA)` | good: ticket → `CONSUMED`, send `PakeConfirmB`. Bad: `BAD_CONFIRMATION`, ticket per §7.2 | `AWAIT_REQUEST` / `CLOSED` |

`AWAIT_REQUEST` then verifies `proof_P` with keys derived from `Ke`; the ticket is already `CONSUMED`.

**Phone states (code):** `CODE_ENTERED → HANDSHAKE → AWAIT_HELLO → AWAIT_PAKE_B → AWAIT_CONFIRM_B →
AWAIT_ACCEPT → SCOPES → AWAIT_DONE → DONE`, with the same failure handling as the QR table; a failed `cB`, a
`BAD_CONFIRMATION` or a timeout during the PAKE returns to `CODE_ENTERED` (owner may retype) and counts toward
the phone-side limit of 3.

**Bound:** an attacker who does not know the code gets one guess per PAKE run (no offline test is possible), at
most 3 runs per code and one code per user-initiated pairing: success probability ≤ 3 × 10⁻⁶ per pairing.

### 7.7 Identity exchange (both flows)

```
PairRequest  { phone_identity_pub: bytes[65], name: string, model: string, os: string,
               proof: bytes[32], sig: bytes[64] }                                 phone → Mac
PairAccept   { mac_identity_pub: bytes[65], mac_presence_pub: bytes[65], mac_name: string,
               scopes_hint: [string], proof: bytes[32], sig: bytes[64], presence_sig: bytes[64] }   Mac → phone
PairComplete { scopes: [string], elevation_required: bool, elevation_scopes: [string], sig: bytes[64] }  phone → Mac
PairDone     { }                                                                   Mac → phone
PairError    { code: enum, detail: string }                                        either
```

Transcripts (field order is normative):

```
T_req = enc("tombolo/pair/v1/request";
            u8(method), exporter_pair, phone_endpoint_id, mac_endpoint_id, n_P, n_M,
            qr_k /* 32 bytes for QR, empty for CODE */,
            phone_identity_pub, name, model, os, seq(phone session ALPNs))
proof_P = HMAC(K_proof_phone, T_req)          sig_P  = Sign(I_P, T_req)

T_acc = enc("tombolo/pair/v1/accept";
            H(T_req), mac_identity_pub, mac_presence_pub, mac_name, seq(scopes_hint), seq(mac session ALPNs))
proof_M = HMAC(K_proof_mac, T_acc)            sig_M  = Sign(I_M, T_acc)       sig_PM = Sign(P_M, T_acc)

T_cmp = enc("tombolo/pair/v1/complete";
            H(T_acc), seq(scopes), u8(elevation_required), seq(elevation_scopes))
sig_C   = Sign(I_P, T_cmp)

pair_id = H(T_cmp)[0..16]
```

What each value proves:

| Value | Proves to the receiver |
|---|---|
| `proof_P` | the phone knows `s` / `Ke` **and** is the TLS peer of this connection (via `exporter_pair`); binds `I_P` and the strings to both |
| `sig_P` | possession of `I_P`, bound to this connection |
| `qr_k` check | the Mac identity key is the one the QR committed to |
| `proof_M` | the Mac knows `s` / `Ke` and is this connection's TLS peer (essential in the code flow) |
| `sig_M` | possession of `I_M`, bound to this connection and to the phone's request |
| `sig_PM` | possession of `P_M`, **and** that the Mac user passed Touch ID / password for this exact transcript |
| `sig_C` | the phone owner accepted exactly these keys with exactly these scopes |

Commit rules: the phone commits its binding **before** sending `PairComplete`; the Mac commits **before** sending
`PairDone` (§4.3 rule 3). The phone's binding stores the Mac's endpoint ID **as seen in TLS**, `I_M.pub`,
`P_M.pub`, `scopes`, the elevation policy, `discovery_key` and `pair_id`; the Mac's stores the phone's endpoint ID,
`I_P.pub`, its own key tags, the scope hint, `discovery_key` and `pair_id`.

**Re-pairing** the same two devices creates a new binding (new keys, new `pair_id`); the commit that inserts it
also marks the old one `REVOKED(REPLACED)` in the same transaction, and sessions on the old binding are ended.
Re-pairing is never merged into an existing binding by name.

### 7.8 Concurrent pairing attempts

| Situation | Behaviour |
|---|---|
| Two connections race for the same QR ticket | The first **valid** proof wins (CAS); see §7.2 for later arrivals. A second valid proof ⇒ `COMPROMISED`, both aborted, user warned |
| Two connections race for the same code ticket | The first `PakeA` takes `IN_USE`; others get `BUSY` before any attempt is charged; after a failed run the ticket returns to `ACTIVE` |
| A connection holds `IN_USE`/`CONSUMED` and stalls | Step timeouts (§7.9) end it; for the code flow the stalled run counts as a failed attempt |
| User opens a second pairing window on the Mac | The previous ticket is killed (one ticket per Mac) |
| Phone scans a second QR / starts a second code entry | The previous attempt is aborted (one attempt per phone) |
| Phone already paired with this Mac | Allowed: re-pairing (§7.7). The old binding stays valid until the new one commits |
| Phone paired with other Macs, or sessions running | Unaffected: pairing uses its own connection and ALPN |
| Pairing message on a `tombolo/1` connection, or session message on `tombolo-pair/1` | Protocol error, connection closed |
| More than 4 unauthenticated connections | New ones refused (protocol §8) |

### 7.9 Timeouts

| Timer | Value | Note |
|---|---|---|
| Ticket TTL (QR and code) | 120 s (60–300 s configurable) | Checked on leaving `ACTIVE` |
| Handshake + `PairHello` | 5 s | Pre-authentication budget |
| Each PAKE step, and `PairRequest` after the last automatic message | 10 s | |
| Mac user confirmation (Touch ID) | 60 s | |
| Phone owner scope selection | 120 s | |
| `PairDone` after `PairComplete` | 10 s | |
| Whole pairing connection | 300 s hard cap | |

### 7.10 Pairing error codes

`UNSUPPORTED_VERSION`, `ROLE_CONFLICT`, `METHOD_MISMATCH`, `NO_TICKET`, `TICKET_EXPIRED`, `TICKET_CONSUMED`,
`BUSY`, `BAD_PROOF`, `BAD_CONFIRMATION`, `BAD_SIGNATURE`, `KEY_MISMATCH` (QR `k` check), `DECLINED`, `TIMEOUT`,
`LIMIT_REACHED`, `COMPROMISED`, `MALFORMED`, `INTERNAL`. The `detail` string is for logs only and MUST NOT
contain secrets.

## 8. Sessions

### 8.1 Handshake and key pinning

- ALPN **`tombolo/1`**, exactly one offered (§16). Mutual raw-public-key TLS (A3).
- The **dialer** knows which binding it is dialing and MUST require the listener's transport key to equal that
  binding's `peer_endpoint_id` (or `peer_pending_endpoint_id`, §13.1).
- The **listener** MUST accept the dialer's transport key only if it is the current or pending endpoint ID of a
  binding with status `UNCONFIRMED` or `ACTIVE`.
- Unknown keys are rejected **silently**: no prompt, no UI, a generic close; a rate-limited local log entry for
  Diagnostics. Revoked keys are treated as unknown.

### 8.2 `Hello` and `SessionAuth` (exporter-bound identity signatures)

```
Dialer                                                         Listener
  ── QUIC/TLS 1.3, ALPN tombolo/1, pinned keys ──▶
  open control stream
  Hello{…, nonce: n_dialer}          ─────────────────────────▶
                                     ◀───────────────────────── Hello{…, nonce: n_listener}
                                     ◀───────────────────────── SessionAuth{sig_L}   (listener can sign as soon as it has sent its Hello)
  SessionAuth{sig_D}                 ─────────────────────────▶
  (MAC side) SessionStart{scopes_requested}  ⇄  (PHONE side) SessionStarted{scopes_granted, …}
```

`Hello` is protocol §3's message with one added field, `nonce` (32 bytes). Then:

```
exporter_session = Exp("tombolo/session/v1")
T_auth(r) = enc("tombolo/session/v1/auth";
                u8(r) /* signer's device role */, "tombolo/1" /* negotiated ALPN */, exporter_session,
                dialer_endpoint_id, listener_endpoint_id, n_dialer, n_listener, pair_id)
SessionAuth.sig = Sign(I_self, T_auth(own role))
```

The verifier rebuilds `T_auth(peer role)` from its own exporter, the TLS-authenticated endpoint IDs, both nonces
and the binding's `pair_id`, and verifies with the binding's `peer_identity_pub` (or
`peer_previous_identity_pub` during rotation, §13.2). The session is **authenticated** when the peer's signature
verifies; until then only `Hello` and `SessionAuth` are accepted, within the 5 s / 16 KiB pre-authentication
budget. A failed verification closes the connection with a generic error (no detail that distinguishes a wrong
key from a wrong transcript).

This binds the hardware identity key of *this binding* to *this TLS connection*: a stolen transport key alone
cannot authenticate a session, and a signature from one connection is useless on any other.

Elevation (Touch ID for control) is **not** part of `SessionAuth`; it is a separate, presence-gated step (§9.3), so
that background continuity sessions (notifications, SMS) work without prompting the Mac user.

### 8.3 Session key schedule and extra connections

```
salt_s     = enc("tombolo/session/v1/salt"; n_dialer, n_listener)
PRK_s      = HKDF-Extract(salt_s, exporter_session)
session_id = HKDF-Expand(PRK_s, "tombolo/session/v1/key/session-id", 16)     -- logs, journal, channel binding
K_bind     = HKDF-Expand(PRK_s, "tombolo/session/v1/key/channel-bind", 32)
```

On paths that use the TLS/TCP fallback with one connection per channel ([ADR-0003](../decisions/0003-transport.md)),
every additional connection is itself a full mutually-authenticated, pinned TLS 1.3 connection with ALPN
`tombolo/1`, and its first message binds it to the session:

```
exporter_channel = Exp("tombolo/channel/v1")                      -- on the NEW connection
T_bind = enc("tombolo/session/v1/channel-bind"; u8(sender role), session_id, exporter_channel, u32be(channel_index))
ChannelBind{session_id, channel_index, mac = HMAC(K_bind, T_bind)}
```

**Extra-connection branch.** An extra connection is told apart from a new session by its first message: `Hello`
starts a session (§8.2); `ChannelBind` starts an extra connection; anything else closes it. For `ChannelBind` the
receiver MUST check, within the same 5 s / 16 KiB pre-authentication budget:

1. the connection's TLS-authenticated peer endpoint ID belongs to the binding of an **`ACTIVE`** session whose
   `session_id` equals the message's `session_id` (otherwise close; no detail is returned);
2. `CT-EQ(mac, HMAC(K_bind, T_bind))`;
3. `channel_index` is one the session has announced on its control stream (`OpenDisplay` → `DisplayOpened`,
   `FileAccept`, …) and is not yet bound; the index is reserved atomically, so two connections cannot claim it.

The channel's type and direction come from that control-stream announcement, never from the extra connection. An
extra connection carries exactly one channel and no control messages, and it is closed when its channel closes or
its parent session leaves `ACTIVE`.

### 8.4 Session state machine (both sides)

| State | Event | Checks | Action | Next |
|---|---|---|---|---|
| `HANDSHAKE` | TLS done | ALPN `tombolo/1`; peer key pinned (§8.1) | dialer: open control stream, send `Hello` (or `ChannelBind` for an extra connection, §8.3) | `AWAIT_HELLO` |
| `AWAIT_HELLO` | `ChannelBind` (listener) | §8.3 extra-connection branch | attach to the parent session | `CHANNEL` (ends with its channel or parent) |
| `AWAIT_HELLO` | `Hello` | nonce ≠ own; fields valid | listener: send `Hello` then `SessionAuth`; dialer: send `SessionAuth` | `AWAIT_AUTH` |
| `AWAIT_AUTH` | `SessionAuth` | `Verify` (§8.2) | phone: promote `UNCONFIRMED` binding to `ACTIVE`; supersede an older session of the same binding (§8.6) | `AUTHENTICATED` |
| `AUTHENTICATED` | Mac: `SessionStart{scopes_requested}` | — | phone computes the grant (§9), starts only allowed channels, replies `SessionStarted` | `ACTIVE` |
| `ACTIVE` | commands, subscriptions | §9 on every one | — | `ACTIVE` |
| `ACTIVE` | elevation, lease events | §9.3, §10 | — | `ACTIVE` |
| any | 5 s pre-auth deadline, bad signature, malformed, unknown message before auth | — | close | `CLOSED` |
| `ACTIVE` | `SessionEnd`, `Unpair`, revocation, supersession, transport loss; **phone: local use or Stop** (§10 rule 4) | — | release the lease (§10), send `SessionEnd{reason}` if possible, stop all channels, close extra connections | `CLOSED` |
| `CLOSED` | any message | — | ignore; connection is closed | `CLOSED` |

A reconnect is always a new session (protocol §8): new handshake, new nonces, new `SessionAuth`, scopes requested
again, elevation again where required.

### 8.5 0-RTT and resumption

Early data (0-RTT) MUST NOT be sent or accepted on `tombolo/1` or `tombolo-pair/1` — not only on the control
stream: replayable data has no place in a remote-control protocol (RFC 8446 §8). TLS session resumption SHOULD be
disabled; it MUST be disabled unless the TLS stack guarantees that a resumed connection reports the original
peer's authenticated raw public key and that the exporter of the resumed connection is fresh. LAN handshakes are
cheap, so v1 disables resumption.

### 8.6 Concurrent sessions

- At most one session per binding. When a new session of the same binding authenticates, the phone ends the older
  one (its lease is released first). This is safe because only an authenticated peer can trigger it.
- A phone MAY have sessions with several Macs at once, but at most **one** session at a time may hold
  `screen.control`; a second Mac's control request is refused with `BUSY` unless the phone owner switches.

## 9. Scopes (phone-authoritative)

### 9.1 Scope definitions

Names from [protocol §2](../protocol.md#2-session-establishment). Direction is stated explicitly because the names
mix perspectives (see §19, D6).

| Scope | Allows | Data direction |
|---|---|---|
| `screen.view` | opening displays and receiving video/audio; listing apps and icons | phone → Mac |
| `screen.control` | input on opened displays: touch, scroll, keys, text, navigation actions, rotation | Mac → phone |
| `notifications.read` | receiving notifications and their removal | phone → Mac |
| `notifications.act` | replying to, dismissing, invoking actions on, and opening notifications; `SetDnd` | Mac → phone |
| `sms.read` | receiving SMS/MMS threads, history, new messages and the SIM list | phone → Mac |
| `sms.send` | sending SMS | Mac → phone |
| `calls.state` | receiving call state and caller ID | phone → Mac |
| `calls.control` | answering, declining, ending, silencing and placing calls | Mac → phone |
| `clipboard.read` | the phone sending its clipboard to the Mac | phone → Mac |
| `clipboard.write` | the Mac setting the phone's clipboard | Mac → phone |
| `files.receive` | the **phone receiving** files the Mac offers | Mac → phone |
| `files.send` | the **phone sending** files to the Mac (always initiated on the phone) | phone → Mac |

**Base messages** need no scope once a session is authenticated: `Hello`, `SessionAuth`, `SessionStart(ed)`,
`SessionEnd`, `Ping`/`Pong`, lease messages, rotation and unpair messages, `Unsupported`, `DeviceStatus`,
`RingDevice`.

### 9.2 Enforcement points

The phone is the only authority. The Mac's `scopes_hint` only shapes its UI.

- **E1 — command gate.** `tombolo-core` on the phone checks every inbound `Envelope` against the session's
  *effective scopes* before dispatching it. Denied commands get `Denied{id, scope}` and are not executed.
- **E2 — data gate.** Every outbound data source checks the scope when the subscription starts **and for every
  item emitted**, so revoking a scope stops the next item.
- **E3 — effect gate.** Platform code that performs a side effect (send SMS, call action, dial, notification
  action, file write, clipboard write) SHOULD re-check the scope through the core immediately before acting.
  Input injection uses a handle that is invalidated atomically when `screen.control`, elevation or the lease ends.
- **E4 — helper gate.** In Enhanced mode the helper accepts capture/injection commands only while the app holds a
  valid lease (S7/S12).

```
gated            = binding.elevation_scopes   if binding.elevation_required, else ∅
effective_scopes = (binding.scopes ∩ session.granted) − (gated − session.elevated_scopes)
```

`session.elevated_scopes` is the **exact** set granted by the last successful elevation (§9.3), not a boolean:
elevating for `screen.view` alone never unlocks `screen.control`.

| Message (protocol §3) | Required scope |
|---|---|
| `OpenDisplay`, `ResizeDisplay`, `CloseDisplay`, `RequestRefresh`, `ReceiverFeedback`, `SetVideoParams`, `ListApps`, `AppIcon`; video and audio channels | `screen.view` |
| `Touch`, `Scroll`, `Key`, `Text`, `NavAction`, `RotateDisplay` | `screen.control` (and `screen.view` for the target display) |
| `NotificationPosted`, `NotificationRemoved` (emitted) | `notifications.read` |
| `NotificationAction`, `NotificationDismiss`, `OpenNotification`, `SetDnd` | `notifications.act` |
| `SmsThreads`, `SmsThreadHistory`, `SmsMessage`, `Subscriptions` (emitted / answered) | `sms.read` |
| `SendSms` | `sms.send` |
| `CallState` (emitted) | `calls.state` |
| `CallAction`, `Dial` | `calls.control` |
| `ClipboardChanged` phone → Mac | `clipboard.read` |
| `ClipboardChanged` Mac → phone | `clipboard.write` |
| `FileOffer` Mac → phone (and its data streams) | `files.receive` |
| `FileOffer` phone → Mac | `files.send` |

**At pairing** the phone owner chooses the scopes; nothing is pre-selected from the Mac's `scopes_hint` without
the owner seeing it. **After pairing** scopes are editable only on the phone; a change is one atomic binding update
(§4.3), takes effect on the next command, stops the affected channels, and is announced to the Mac with
`ScopesChanged{scopes}`.

### 9.3 Elevation (hardware-enforced "ask every time")

If `binding.elevation_required` is true (default), scopes in `binding.elevation_scopes` (default `screen.view`,
`screen.control`) are usable only while the session is **elevated**:

```
Mac → ElevationBegin{scopes}            (when the user opens the mirror window, or starts control)
Phone → ElevationChallenge{n_E}         (fresh 32-byte phone nonce; one outstanding; valid 60 s)
Mac: Touch ID / password prompt "Control <phone name>?" → Secure Enclave signs with P_M
T_elev = enc("tombolo/session/v1/elevate";
             exporter_session, dialer_endpoint_id, listener_endpoint_id, n_dialer, n_listener,
             pair_id, n_E, seq(scopes))
Mac → ElevationProof{sig = Sign(P_M, T_elev)}
Phone: Verify with binding.peer_presence_pub; n_E single-use → ElevationGranted{scopes}
```

The phone sets `session.elevated_scopes := binding.scopes ∩ binding.elevation_scopes ∩ scopes` (replacing, not
adding to, any earlier value) and reports it in `ElevationGranted`. `session.elevated_scopes` becomes empty on
lease release (§10, subject to the grace rule there), idle timeout (default 15 min without input or open
display), and any change of `binding.scopes` or the elevation policy; the session itself ends on local use,
**Stop**, revocation and session end (§10 rule 4).

Because the signature comes from a Secure Enclave key whose every use requires user presence, and the phone (not
the Mac app) verifies it, "ask every time" is enforced end-to-end by hardware: Mac malware that can drive the
Tombolo app still cannot produce an elevation without the user passing Touch ID or typing the Mac password.

## 10. Lease (fail-closed control)

> This section is the **lease contract proposed to P0-07 (S7)**. Every number is *(to confirm with P0-07, S7
> spike)*; the semantics are normative.

**Lease-gated resources:** every open display and capture, every input-injection path (Standard: Accessibility
gestures and input method; Enhanced: helper injection/UHID), turning the phone's display off, and any helper action.
Continuity channels (notifications, SMS, files, clipboard) are **not** lease-gated; they end with the session.

| Parameter | Proposed value |
|---|---|
| Challenge interval (phone sends `LeaseTick`) | **250 ms** *(to confirm with S7)* — the Mac answers each tick, so it renews every ~250 ms |
| Lease length `L` (phone monotonic clock, from the *issue time of the tick* the Mac answered) | **1000 ms** *(to confirm with S7)* |
| Maximum answer age accepted | 500 ms after the tick was issued *(to confirm with S7)* |
| Release completion after expiry | ≤ 250 ms target *(to confirm with S7)* |
| Local-use quiet period before screen access may resume | 5 s without local input *(to confirm with S7)* |

**Rules:**

1. The lease starts when the phone sends `DisplayOpened` (or grants elevation, whichever is first), with
   `deadline = now + L`.
2. **Renewal is challenge–response, paced by the phone,** so that renewals delayed or buffered by the network can
   never extend the lease. While any lease-gated resource is active the phone sends
   `LeaseTick{tick: u64}` every 250 ms (QUIC datagram; on the control stream where the path has no datagrams),
   with `tick` strictly increasing, and remembers each tick's issue time on its monotonic clock. The Mac answers
   every tick it receives with `LeaseRenew{tick}`. The phone accepts a renewal only if it arrives on the session's
   own connection, echoes a tick the phone actually issued, is newer than the last accepted tick, and arrives no
   more than 500 ms after that tick's issue time. It then sets `deadline = issue_time(tick) + L` — relative to when
   the **phone** issued the challenge, never to when the answer arrived, and never using a Mac timestamp.
   Consequently, if the Mac stops at time `t0`, the newest tick it can have answered was issued at or before `t0`,
   and the lease ends no later than `t0 + L` however the network delays packets.
3. **Expiry is decided on the phone without any message from the Mac.** On expiry the phone MUST: stop injection and
   release every pressed pointer and key (synthesise up/cancel), stop capture and close video/audio channels,
   close virtual displays, restore display power, revoke helper rights, and send `LeaseReleased{reason}` if the
   connection is still up.
4. **Immediate release (no waiting for the timeout)** on: local touch or key input, power button, keyguard shown,
   screen turned off by the user, **Stop** (notification, Quick Settings tile, status chip), revocation, a scope
   change removing `screen.*`, session end or supersession, app or helper death (detected by the independent cleanup
   process of S7, which treats loss of the app's own heartbeat as expiry). In addition:
   - **Local use and Stop end the session** ([architecture §8](../architecture.md#8-security-model): ending the
     session on local use is mandatory). The phone sends `SessionEnd{LOCAL_USE | STOPPED}`, transitions to `CLOSED`
     (§8.4), rejects every further message on that connection, and closes it and every extra connection (§8.3).
   - After **local use**, the phone refuses `OpenDisplay` and `ElevationBegin` from any Mac until the phone has seen
     no local input for the quiet period (5 s), so the Mac cannot immediately take control back.
   - After **Stop**, the phone sets the binding's persisted `screen_paused` flag: it refuses `OpenDisplay` and
     `ElevationBegin` from that Mac until the phone owner taps **Resume** on the phone. Continuity scopes may
     reconnect in a new session; screen access may not.
5. The Mac MUST stop answering ticks — and SHOULD send `LeaseRelease` — when it sleeps, locks its screen, quits,
   closes the last mirror window, or the user disconnects. Correctness never depends on these messages.
6. After any release the Mac must send `OpenDisplay` again. Elevation is cleared on every release; the phone MAY
   keep `session.elevated_scopes` across a release with reason `TIMEOUT` if the same connection resumes within 10 s
   *(open question Q9)*. Releases for local use, keyguard, Stop or revocation always clear it (and the first two
   end the session anyway).
7. Worst-case time from an event the phone cannot observe (link loss, Mac crash) to completed release is
   `L + release completion` ≈ 1.25 s with the proposed numbers, which is **longer than S7's "within 1 s"
   criterion**. S7 must either accept ~1.25 s for unobservable events or lower `L` (e.g. 750 ms) — flagged for P0-07.
   Events the phone observes itself (rule 4) are bounded by the release completion time alone.
8. The phone shows the status chip, Quick Settings tile and ongoing notification with **Stop** whenever any
   lease-gated resource is active, and logs the session (which Mac, start, end, elevations).

## 11. Side-effect binding (`op_id`)

Protocol §8 binds each side-effecting command's `op_id` to "a hash of the payload". The hash is computed by the
phone from the received fields, never from Protobuf bytes:

```
op_hash = H(enc("tombolo/op/v1/<kind>"; op_id, <fields>))
```

| `<kind>` | Fields after `op_id` (in order) |
|---|---|
| `send-sms` | `i32be(subscription_id)`, `seq(address…)` (message order), `text` |
| `call-action` | `call_id` (UTF-8), `u8(action)` with ANSWER=1, DECLINE=2, END=3, SILENCE=4 |
| `dial` | `number` (UTF-8, as sent) |
| `notification-action` | `key`, `action_id`, `seq(reply_text)` (empty `seq()` when absent) |
| `file-offer` | `transfer_id` (16 bytes), `seq(item…)` where `item = seq(name, u64be(size), mime, blake3[32])` |

The journal is keyed by `(pair_id, op_id)`. The same `op_id` with a different `op_hash` is rejected (protocol §8).
Including the kind label prevents an `op_id` reused across kinds from matching.

**Making the retention rule enforceable.** Protocol §8 keeps journal records for 7 days and rejects an `op_id`
"older than the retention window" — but a random UUID carries no age, so once its record is deleted an accidental
resubmission would look new. Therefore:

- `op_id` MUST be a **UUIDv7** (RFC 9562), whose first 48 bits are the Mac's Unix time in milliseconds.
- The phone MUST NOT execute an operation whose embedded time is more than **6 days** in the past or more than
  **1 day** in the future by the phone's clock; it replies `EXPIRED` instead.
- Journal records are kept for at least **7 days** after insertion. Because acceptance (≤ 6 days old, ≤ 1 day ahead)
  is strictly inside retention, any `op_id` the phone could still accept is still in the journal, so a duplicate is
  always recognised.

The embedded time is supplied by the Mac and is not authenticated as a time; that is sufficient, because the rule
guards against accidental replays by the authenticated, paired Mac — a malicious paired Mac holding `sms.send` can
simply send new messages.

## 12. Discovery token

The phone's DNS-SD TXT record carries `v=1` and `t=<b64u(slots)>` ([architecture §7](../architecture.md#7-discovery-and-connection)).

```
epoch            = floor(unix_seconds / 900)
token(DK, e)     = HMAC(DK, enc("tombolo/discovery/v1/token"; u64be(e)))[0..8]
filler(FK, e, i) = HMAC(FK, enc("tombolo/discovery/v1/filler"; u64be(e), u8(i)))[0..8]
slots            = the tokens of all UNCONFIRMED/ACTIVE bindings for epoch e, plus fillers i = 0, 1, …
                   until there are 4 slots (8 if the phone has more than 4 bindings),
                   sorted by byte-wise ascending order and concatenated
```

- `DK` is the binding's `discovery_key` from the pairing key schedule (§7.4) — derived from the exporter and the
  method secret, **not** from the QR secret alone, so a photo of the QR does not let anyone track the phone later.
- Fillers make the number of paired Macs invisible up to 4; sorting hides which slots are real. `FK` is a
  phone-local random key, so fillers are stable within an epoch (re-announcements look identical) and
  unpredictable across epochs.
- A Mac matches a phone if any slot equals that binding's token for epoch `e−1`, `e` or `e+1` (clock skew).
- The token is only a hint: identity is always proven by the handshake. Within one epoch, an observer present on
  two networks can link sightings (residual risk accepted in architecture §7).
- A revoked binding's token disappears from the next announcement; the phone re-announces immediately after a
  revocation.

## 13. Key rotation

All rotations happen inside an **authenticated session** and follow §4.3 (atomic, commit-before-ack).

### 13.1 Transport key

1. Device X sends `RotateTransport{new_endpoint_id}`. Peer Y stores it as `peer_pending_endpoint_id` (atomic) for at
   most 10 minutes and replies `RotateTransportPending`.
2. X opens a new `tombolo/1` connection using the new key. Y accepts the pending key (§8.1). When `SessionAuth` on
   the new connection verifies with the **same binding's** identity key, Y atomically sets `peer_endpoint_id := new`,
   clears the pending value, increments `generation`, and replies `RotateTransportDone`.
3. X uses one transport key for all its bindings, so X keeps the old key until every binding has completed step 2,
   or 30 days have passed; bindings that never complete are marked stale and need re-pairing.

v1 MAY implement transport-key rotation as re-pairing only (§20, Q11).

### 13.2 Identity and presence keys

```
T_rot = enc("tombolo/session/v1/rotate-key";
            u8(signer role), u8(kind) /* 1 = identity, 2 = presence */, rotation_id /* 16 bytes */,
            exporter_session, dialer_endpoint_id, listener_endpoint_id, n_dialer, n_listener,
            pair_id, old_pub, new_pub)
RotateKey{kind, rotation_id, old_pub, new_pub,
          sig_auth = Sign(K_auth, T_rot), sig_new = Sign(new key, T_rot)}
```

- `K_auth` is the identity key X used for **this session's** `SessionAuth`. `sig_new` proves possession of the new
  key; for a presence key it requires Touch ID, so it also proves the Mac user was present.
- **Initiator state (X).** Before sending, X creates the new hardware key and durably records
  `pending_rotation = {rotation_id (16 random bytes), kind, old alias, new alias}` in its binding. At most one
  rotation per binding is pending on either side; X does not start another until the pending one is resolved.
- **Identity key (Y).** Y verifies `sig_auth` with the key that verified this session's `SessionAuth` and `sig_new`
  with `new_pub`, checks `old_pub` equals that key, and then — in one transaction — sets
  `peer_identity_pub := new_pub`, `peer_previous_identity_pub := old_pub`, records `last_rotation_id := rotation_id`,
  increments `generation`, and replies `RotateKeyDone{rotation_id}`. Y keeps accepting the previous key in
  `SessionAuth` until the first session that verifies with the new one, then clears it.
- **Retry after a lost acknowledgement.** If X never received `RotateKeyDone`, it still holds `pending_rotation`,
  signs its next `SessionAuth` with the **old** key (which Y accepts as `peer_previous_identity_pub`), and re-sends
  `RotateKey` with the **same** `rotation_id`, `old_pub` and `new_pub` and fresh signatures over the new session's
  `T_rot`. If Y's `last_rotation_id`, previous key and current key already equal that rotation, Y changes nothing and
  replies `RotateKeyDone` (idempotent). A `RotateKey` with a different `rotation_id` while Y still holds a previous
  key is refused with `BUSY`.
- **Completion (X).** On `RotateKeyDone{rotation_id}` X, in one transaction, makes the new key current and clears
  `pending_rotation`, then deletes the old key.
- **Presence key (Mac).** Same messages with `kind = 2`; `K_auth` is still the Mac's identity key. Before committing,
  the phone additionally requires the **phone owner's approval on the phone** ("The Touch ID key of <Mac> changed —
  allow?"). Without this, Mac malware able to use the identity key could swap in a presence key it controls and
  bypass elevation. The phone does not keep a previous presence key.
- Triggers: the Secure Enclave invalidated a key (e.g. a presence key created with `.biometryCurrentSet` after a
  fingerprint change), a user-requested key refresh, a policy change. A device that has lost an identity key
  outright (hardware reset, app reinstall) cannot rotate and must re-pair.

### 13.3 Discovery key

Key rotation does **not** change `discovery_key`; it changes only when the devices re-pair. (Deriving a new one
from the session in which a rotation commits would let the two sides diverge when an acknowledgement is lost.)
The discovery key protects only against tracking, and it is stored with the same protection as the binding.

## 14. Device loss and recovery

| Event | What happens |
|---|---|
| **Mac lost or stolen** (T7) | The phone owner revokes the Mac on the phone (§15): immediate and complete, because the phone is the authority. Until then a thief needs the Mac password or Touch ID to elevate (control and screen), but continuity data (notifications, SMS if granted) flows to an unlocked, logged-in Mac — the session log and "connected Macs" list on the phone make this visible |
| **Phone lost or stolen** (T9) | The Mac user removes the phone on the Mac: the Mac stops accepting it and deletes its per-binding keys. The phone's keys stay in its Keystore; the Mac auto-accepts files only from an unlocked phone (phone reports lock state) |
| **New device, OS reinstall, app reinstall, app data cleared, backup restore** | Keys do not migrate (non-exportable, excluded from backup). The device pairs again from scratch; the peer keeps a stale binding that can never authenticate. The peer's UI offers to remove a binding that has not connected for 30 days or whose name matches a newly paired device — but MUST NOT merge or replace it automatically by name |
| **Hardware key invalidated** (Keystore reset, Secure Enclave key deleted) | Signing fails: the binding is unusable; the UI prompts re-pairing. If only the presence key is gone, a presence rotation (§13.2) with phone approval is possible |
| **Transport key file lost or corrupted** | The device generates a new transport key; every binding is stale (the peer pins the old endpoint ID) and must be re-paired, unless an old session is still open, in which case §13.1 applies |

There is no recovery code, no cloud escrow and no weaker re-pairing path: recovery is always a full pairing.

## 15. Revocation and its propagation

**Local revocation** (either side, "Forget this device", or "Remove this Mac" on the phone) is immediate and does
not depend on the peer:

1. One transaction: binding `status := REVOKED`, `revoked_at` set, `discovery_key` wiped. A tombstone (pair ID,
   peer endpoint ID, fingerprint of the peer identity key, reason, time) is kept for 30 days for the log and UI and
   MUST NOT be used to accept anything.
2. Delete this side's per-binding hardware keys (identity; on the Mac also presence). From now on nothing can
   authenticate this pairing in either direction, whatever the peer still stores.
3. End any session of this binding. On the phone this is a lease release event (§10 rule 4): control and capture stop
   at once.
4. Phone: re-announce DNS-SD without the binding's token. Mac: SHOULD purge cached phone data (notifications, SMS
   cache, thumbnails).

**Propagation:**

- If a session is open, the revoking side sends `Unpair{reason}` on the control stream before closing. It is
  authenticated by the session (§8.2); the receiver performs steps 1–4 itself and tells its user ("<name> removed
  this pairing").
- If no session is open, nothing is sent. The stale side learns lazily: its next connection is rejected as an
  unknown key (§8.1). After repeated rejections it shows "Can't reach <name>; it may have removed this pairing",
  with a **Remove** action. A stale binding grants nothing, because the revoking side's keys no longer exist.
- `Unpair` is accepted only inside an authenticated session of that binding; pre-authentication errors never delete
  a binding.
- **Stop ≠ revoke:** Stop ends the current session and lease and pauses screen access for that Mac until the owner
  resumes it (§10 rule 4); the binding stays.
- In 0.1–0.2 the ADB path is separate: revoking a Tombolo binding does **not** revoke ADB debugging authorisations.
  The UI MUST say so and link to the system setting.

## 16. Downgrade handling

- **TLS 1.3 only**, rustls default cipher suites, Ed25519 raw public keys only. No TLS 1.2, no plaintext mode, no
  "debug" ALPN, no build flag that disables pinning in release builds.
- **ALPN:** `tombolo/1` for sessions, `tombolo-pair/1` for pairing. A dialer offers exactly one. A listener selects
  exactly that one or fails with `no_application_protocol`. A pairing ALPN is never negotiated when a session ALPN
  was offered, or vice versa.
- **No fallback retries.** After a failure, a device MUST NOT retry with an older protocol version, a different
  ALPN, a different pairing method or a weaker path. Moving between transport paths (Wi-Fi QUIC, USB, TLS/TCP
  fallback) is not a downgrade: every path runs the same TLS 1.3 authentication and this specification unchanged.
- **Future versions:** when `tombolo/2` exists and N−1 support is required (protocol §7), the dialer offers its
  versions in preference order; the TLS handshake transcript protects the offer list, and `T_auth` carries the
  selected ALPN. The binding records the highest version the peer has authenticated with, and a device MUST refuse a
  later session with that peer at a lower version unless the user explicitly re-pairs.
- `Hello.proto_minor` and capabilities MUST NOT switch any security mechanism on or off; everything in this
  document is mandatory in major version 1.
- **Pairing method:** the method is in `PairHello` and in every pairing transcript. An attacker cannot turn a QR
  pairing into a code pairing without the user typing a code shown on the Mac.

## 18. Test vectors

Generated deterministically by [`tools/pairing-vectors/`](../../tools/pairing-vectors/) (see its README for
commands, including `--check`). Every vector lists its inputs (keys from fixed scalars, a fixed stand-in for the TLS
exporter, fixed nonces), every intermediate transcript in hex, and the outputs.

| File | Covers |
|---|---|
| `encoding.json` | `LP`, `enc`, `seq`, nested `seq`, empty fields; P-256 `SPKI` and `k`; must-reject inputs |
| `spake2-rfc9382.json` | RFC 9382 Appendix B vectors reproduced by our implementation (cross-check), plus `M`/`N` regenerated with the RFC's Appendix A procedure |
| `ecdsa-rfc6979.json` | RFC 6979 §A.2.5 P-256/SHA-256 signatures reproduced by the signing code used for every other vector; DER ↔ `r ‖ s` conversion |
| `qr-pairing.json` | QR payload, pairing key schedule, `T_req`/`T_acc`/`T_cmp`, proofs, signatures, `pair_id`, discovery key |
| `code-pairing.json` | `pw`, `w`, SPAKE2 messages, `TT`, `Ke`/`Ka`/`KcA`/`KcB`, `cA`/`cB` from fixed scalars; the identity exchange; wrong-code and invalid-point negative cases |
| `session.json` | `T_auth` both directions, `SessionAuth` signatures, session key schedule, channel binding, elevation, key rotation; negative cases |
| `discovery.json` | epochs, tokens, fillers and the TXT value |
| `op-payload.json` | `op_hash` for every side-effect kind |

Signatures use RFC 6979 deterministic nonces (cross-checked against RFC 6979 §A.2.5); real hardware signatures
differ and implementations test them by verification.

```sh
cd tools/pairing-vectors
cargo run --release               # regenerate the JSON files
cargo run --release -- --check    # exit 1 if the committed files differ from the generator, 2 if a self-test fails
```

Every run first reproduces the RFC 9382 Appendix B vectors (and regenerates `M`/`N` per Appendix A) and the
RFC 6979 vectors, and refuses to write anything if one differs.

## 19. Differences from the existing documents

These are deliberate and are proposed as follow-up edits to the documents named (not made here, because this task
owns only `docs/security/**`).

| # | Document | Says | This spec | Why |
|---|---|---|---|---|
| D1 | [ADR-0005](../decisions/0005-pairing-and-identity.md) consequences | PAKE "implemented … (RustCrypto `spake2`)" | Own RFC 9382 P-256 implementation in `tombolo-core` | RustCrypto `spake2` 0.4.0 and 0.5.0-pre.0 implement only Ed25519 with a python-spake2/magic-wormhole-style transcript, not RFC 9382's P-256 suite. The generator here implements RFC 9382 on `p256` and reproduces all four RFC vectors |
| D2 | [protocol §2](../protocol.md#2-session-establishment) step 4, [architecture §8](../architecture.md#8-security-model) | Touch ID is required for the `SessionAuth` signature when "ask every time" is on | `SessionAuth` uses a non-presence identity key; Touch ID gates a separate elevation signed by a presence key and verified by the phone (§9.3) | A presence-gated session key would block background continuity sessions; a separate elevation keeps "ask every time" hardware-enforced and phone-verified |
| D3 | [architecture §7](../architecture.md#7-discovery-and-connection), [research §4.3](../research/04-transport-and-security.md#43-tombolo-discovery-design) | Discovery key "derived from the pairing secret"; token = HMAC(pairing secret, epoch) | Derived from the exporter **and** the method secret (§7.4); fillers hide the binding count (§12) | Anyone who photographed a QR could otherwise track the phone forever; the code flow has no 256-bit secret at all |
| D4 | [research §5.3](../research/04-transport-and-security.md#53-tombolo-pairing-design) | Code "shown on the phone, typed on the Mac" | Shown on the Mac, typed on the phone (as protocol §6) | One direction for both flows: the Mac creates and enforces every pairing secret; the owner of the high-value device types into it |
| D5 | [ADR-0005](../decisions/0005-pairing-and-identity.md), research §5.3 | One identity key per device | One identity key **per binding** (§4.1) | Unpairing deletes the only key that can authenticate that pairing, on either side ("unpairing on either side revokes both keys" becomes literally true); no cross-pairing linkability |
| D6 | [protocol §2](../protocol.md#2-session-establishment) scope names | `files.receive`/`files.send` are named from the phone's view; `clipboard.read`/`sms.send` etc. from the Mac's | Names kept; direction stated explicitly in §9.1 | Mixed perspectives invite enforcement bugs; renaming (e.g. `files.to_phone` / `files.to_mac`) is proposed for the maintainers |
| D7 | [protocol §2](../protocol.md#2-session-establishment) | One "session nonce" | Each side contributes its own nonce in `Hello` (§6) | Nonce ownership: each side gets freshness from its own randomness |
| D8 | [protocol §2](../protocol.md#2-session-establishment) | 0-RTT disabled "for the control stream" | Disabled for both ALPNs entirely; resumption disabled (§8.5) | Simpler and removes replayable data from every channel |
| D9 | [protocol §3](../protocol.md#3-control-messages-sketch) | `Dial{number}` has no `op_id`; §8 lists `Dial` as a side effect | `Dial` carries `op_id` (§11) | Consistency with protocol §8 |
| D10 | [protocol §6](../protocol.md#6-pairing-messages) | Two-message pairing (`PairRequest`, `PairAccept`) | Adds `PairHello`, `PairComplete`, `PairDone` | Nonce exchange before any proof; the phone owner's scope choice and both commits need explicit messages |
| D11 | [protocol §8](../protocol.md#8-robustness-rules) side effects | `op_id` is a UUID; ops older than the 7-day retention are rejected | `op_id` is a UUIDv7; acceptance window 6 days back / 1 day ahead, strictly inside retention (§11) | A random UUID carries no age, so the protocol §8 rule could not be enforced after a record expires |
| D12 | [architecture §8](../architecture.md#8-security-model) | Fail-closed via a lease the Mac renews | The phone paces renewals with `LeaseTick` challenges and measures the lease from its own issue time (§10 rule 2) | A Mac-paced renewal can be delayed and replayed in order by the network, stretching the lease past its bound |

## 20. Open questions for the reviewer

1. **Exporter binding.** Is `Exp(label)` with an empty context plus our own transcripts sufficient channel binding
   for raw-public-key QUIC (A2/A3), given that S5 has not yet confirmed exporter access in iroh/noq?
2. **Labels.** RFC 5705 reserves labels beginning with `EXPERIMENTAL` for private use without registration. Should
   our exporter labels (`tombolo/pair/v1`, `tombolo/session/v1`, `tombolo/channel/v1`) use that prefix, or be
   registered?
3. **No MHF for `w`.** RFC 9382 says `w` SHOULD come from a memory-hard function. We use HKDF because the password is
   single-use and connection-bound (online guessing only). Is that acceptable?
4. **SPAKE2 identities and AAD.** A and B are the TLS-authenticated endpoint IDs; AAD carries both pairing nonces and
   the ALPN list. Is that the right binding, or should the identity keys be bound into the PAKE too?
5. **No extra AEAD layer.** Protocol §6 says "inside the PAKE-derived channel"; we MAC every identity value with
   PAKE-derived keys inside TLS instead of adding a second AEAD channel (§7.6). Any weakness?
6. **Presence key policy.** `.userPresence` permits the Mac password as a fallback (T7 residual);
   `.biometryCurrentSet` does not, but is invalidated by fingerprint changes and is unavailable on Macs without
   Touch ID. Which default?
7. **Per-binding identity keys** (D5) versus one per device: any downside we missed (key-store limits, StrongBox
   key-count or latency limits — S10 measures latency)?
8. **T12 race.** Should the QR flow add a short confirmation code displayed on both screens, given users rarely
   compare such codes? Is the "second valid proof ⇒ compromised" rule enough?
9. **Lease grace.** May the phone keep elevation across a pure timeout release if the same connection resumes within
   10 s (§10 rule 6), or must every release clear it?
10. **Invalid QR proofs.** Each invalid proof costs the ticket one of 3 attempts, which lets a LAN attacker cancel a
    pairing (DoS, visible to the user). Is the trade-off right for a 256-bit secret, or should invalid proofs only
    be rate-limited?
11. **Transport-key rotation** (§13.1) across several bindings is complex; is "rotation = re-pair" acceptable for v1?
12. **Signature encoding.** Fixed `r ‖ s`, no low-S requirement. Any reason to require low-S or DER?
13. **Discovery token.** 8-byte tokens, 15-minute epochs, 4 sorted slots with fillers: adequate for the stated
    privacy goal? Should the slot count be larger?
14. **Android key attestation.** Should the Mac verify the phone identity key's attestation chain (hardware level)
    at pairing, given the privacy cost of attestation certificates?
15. **Transcript format.** Any concern with `enc()` (u32 length prefixes, field count, label first) or with chaining
    `H(T_req)` → `T_acc` → `T_cmp` instead of carrying the full transcript?
16. **Session supersession** (§8.6): the newest authenticated session of a binding replaces the older one. Any abuse
    by an attacker holding a stolen transport key but not the identity key? (We believe not: supersession happens only
    after `SessionAuth`.)
